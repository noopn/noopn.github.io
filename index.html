DFA 最小化（DFA Minimization）是形式语言与自动机理论中极其优美的一部分。

如果说 子集构造 解决了 “从不确定到确定”，那么 DFA 最小化 解决的就是 “从冗余到精简”。

下面为你系统梳理 DFA 最小化的全套理论知识体系。

一、核心理论基石：为什么一定能最小化？

1. Myhill-Nerode 定理（极小 DFA 唯一性定理）

定理：对于任意一个正则语言 $L$，存在且仅存在一个状态数最少的 DFA（在状态重命名的同构意义下唯一）。

这意味着：无论你的 NFA 有多乱，转换出来的原始 DFA 有多么庞大，只要经过最小化，它们最终都会殊途同归，缩减成那个结构完全相同的、最完美的极小自动机。

2. 不可区分性（Indistinguishability）与状态等价

怎么知道两个状态 $p$ 和 $q$ 能不能合并？
理论上采用 “黑盒测试实验”：

假设你站在状态 $p$，另一个人站在状态 $q$。我们给你们两个人输入同一个任意字符串 $w$：

  • 如果你走完 $w$ 到达了接受状态，而他走完 $w$ 到达了拒绝状态，那么字符串 $w$ 就把你们两个人区分开来了，称 $w$ 为 区分串（Distinguishing String）。
  • 如果没有任何字符串 $w \in \Sigma^$* 能够把你们区分开来——也就是说，无论喂什么后续字符串，你们要么同时接受，要么同时拒绝，那么状态 $p$ 和 $q$ 就是 等价的（Equivalent），记作：
    $$p \sim q$$

等价状态的核心结论：

如果两个状态是等价的，外界任何输入都无法探测出它们俩的区别。因此，把它们合并为一个状态，绝不会改变自动机对任何语言的识别结果。

二、从无限到有限：$k$-等价性（$k$-Equivalence）理论

我们不可能用无穷多个字符串去逐一测试状态等价性。理论上是如何将其转化为有限步计算的？

答案是：按测试字符串的长度 $k$ 进行分层归纳（$k$-等价）。

等价层级 数学定义 直观含义 分组判据
$0$-等价 ($\sim_0$) 无法被长度为 0 的字符串（即空串 $\epsilon$）区分 还没输入任何字符就露出破绽 同为接受状态，或同为非接受状态
$1$-等价 ($\sim_1$) 无法被任何长度 $\le 1$ 的字符串区分 消耗任意单个字符后，行为依然一致 在任何单字符转移后，落入同一个 $0$-等价组
$k$-等价 ($\sim_k$) 无法被任何长度 $\le k$ 的字符串区分 消耗任意 $\le k$ 长度的字符串，行为依然一致 在任何单字符转移后，落入同一个 $(k-1)$-等价组

$k$-等价的递推核心公式：

状态 $p$ 与 $q$ 是 $k$-等价的，当且仅当：

  1. $p$ 和 $q$ 本身是 $(k-1)$-等价的；
  2. 对于字母表中的任意输入字符 $a \in \Sigma$：
    $$\delta(p, a) \sim_{k-1} \delta(q, a)$$

通俗理解：如果我知道你们在测试长度为 $k-1$ 的字符串时是分不出区别的，那么要测长度为 $k$ 的串，只需要让你们每人先走一步（吃进一个字符 $a$），看你们走到的新状态是不是属于同一伙人（$(k-1)$-等价组）。如果是，那在长度 $k$ 上你们依然无法被区分！

三、算法推演机制：分区细化（Partition Refinement）

这个算法在学术上通常被称为 Moore 状态最小化算法（也是 dfa-minimizer.js 源码所实现的机制）。

它的运作方式是：从最粗的粗粒度划分开始，不断用转移去向把集合“切碎”，直到切不动为止。

graph TD
    A["初始全集 Q"] --> B["【第 0 轮：0-等价划分 P₀】\n切成两块：[非终态组, 终态组]"]
    B --> C["【第 1 轮：1-等价划分 P₁】\n检查每组内状态在输入字符后，目标是否在 P₀ 的同一块中？\n若去向不同 -> 细分切开"]
    C --> D["【第 k 轮：k-等价划分 P_k】\n检查每组内状态在输入字符后，目标是否在 P_{k-1} 的同一块中？\n若去向不同 -> 细分切开"]
    D --> E{"P_k 是否与 P_{k-1} 完全相同？\n(划分达到不动点 Fixed Point)"}
    E -- "否 (仍有集合被切开)" --> D
    E -- "是 (再也切不开了)" --> F["【算法收敛】\n每个最终子块就是一个等价类\n合并为一个新状态，重建极小 DFA"]

算法必定终止的数学证明（收敛性）：

  1. 单调性：集合只能被拆分（Refine），绝不可能发生两个集合重新合并的情况。
  2. 有限性：总状态数 $|Q| = n$ 是有限的。一个拥有 $n$ 个元素的集合，最多只能被切成 $n$ 个单元素子集。
  3. 步数上界：每一轮至少要切出一刀，如果不发生拆分就会立即终止。因此算法最多在 $n - 1$ 轮内必定收敛停机！

四、最终重构：商自动机（Quotient Automaton）

当分区细化终止后，我们得到了一组最终的互不相交的等价类子集：
$$\mathcal{P} = { [q_1], [q_2], \dots, [q_m] }$$

如何用这组集合构建最小化 DFA？
形式语言理论中称此为构建 **商自动机（Quotient Automaton） $M / \sim$**：

  1. **新状态集 $Q’$**：每个等价类作为一个新状态（例如类 ${2, 3, 4}$ 变成单个新状态 2）。
  2. **新起始状态 $q_0’$**：包含原起始状态 $q_0$ 的那个等价类 $[q_0]$。
  3. **新终态集 $F’$**：所有由原终态组成的等价类。
  4. **新转移函数 $\delta’$**：
    $$\delta’([q], a) = [\delta(q, a)]$$
    • 理论良定义（Well-defined）保证：从等价类 $[q]$ 中随便挑出哪一个代表状态，计算其在字符 $a$ 下的转移，其结果落入的等价类都绝对是同一个！这是等价类数学性质严格保证的。

总结六字诀

理解 DFA 最小化，只需记住六个字：

  • 区分（Distinguish）：只要有任意后续输入能让一个接受、一个拒绝，就必须分开；
  • 细化（Refine）：按转移目标一步步细分，能分则分；
  • 合并（Merge）：既然无论怎么输入都完全分不开，就彻底打包成一个状态。
    在 dfa-minimizer.js 中，DFA 最小化采用的是经典编译原理中的 $k$-等价性状态划分算法（$k$-Equivalence Partition Refinement / Moore 算法）。

其核心思路是：寻找行为完全等价的状态并将它们合并为一个超级状态。如果两个状态在面对任意后续字符输入时，走向的接受/拒绝结论完全一致，那么它们就是等价的，保留多个只是冗余。

二、核心数据结构

在阅读代码前，先理解这几个核心变量的作用：

  1. **currentTransitionMap**（全局/闭包映射字典）：
    • 结构：{ [stateNumber]: Set }
    • 作用：记录每个原始状态当前属于哪一个集合（划分块）。
    • 例如状态 2 和状态 3 同在终态组 S_accept，则 currentTransitionMap[2] === S_accept，currentTransitionMap[3] === S_accept。
  2. **all**（历史划分栈）：
    • all[0]：0-等价的分组结果 [nonAccepting, accepting]
    • all[1]：1-等价的分组结果
    • all[N]：最终稳定的分组结果
  3. **remaped**（Map<Set, number>）：
    • 将最终合并后的每一个 Set（等价集合），重新赋予一个精简的状态编号（如 1, 2, …）。

1. 阶段 0：构建 0-等价初始划分（行 20 ~ 51）

  • 原理解析：
    • 0-等价 代表消耗空串 $\epsilon$ 后的行为：终态直接接受，非终态不接受。

2. 阶段 1：循环细化（1..N-等价）（行 53 ~ 109）

  • 细化过程机制：
    1. 对当前集合 set = [A, B, C]：
    2. 先把 A 放入新组：Group1 = {A}。
    3. 检查 B：调用 areEquivalent(B, A, ...)。
      • 如果等价，Group1.add(B)，变成 {A, B}；
      • 如果不等价，为 B 创建新组 Group2 = {B}。

两个状态在当前轮次下被判定为等价的前提是：在字母表的所有字符上，它们的目标去向必须一致。

代码实现细节探讨：
在经典的 Moore 算法中，两个状态在字符 $c$ 上的转移 $\delta(s_1, c) = t_1$ 与 $\delta(s_2, c) = t_2$ 等价的充要条件是 $t_1$ 和 $t_2$ 落在同一个划分块中，即 currentTransitionMap[t1] === currentTransitionMap[t2]。

Location API (获取与操作 URL)

window.location:

  • assign(url): 导航到新地址（产生历史记录）。

  • replace(url): 导航到新地址（不产生历史记录，直接替换当前页）。

  • reload(): 刷新当前页。

History API

  • history.state 只读属性，返回当前历史条目关联的状态对象。

    当页面刷新后，或者通过代码逻辑回到某个历史点时，你可以直接通过 history.state 拿到之前存进去的那个 JSON 对象，而不需要等待 popstate 事件。

  • history.pushState(state, title, url) 增加一个历史记录条目，但是不会触发 popstate 事件， 也不会刷新页面。

    state 参数：它可以是任何可以被序列化的对象（即可以用 JSON.stringify 处理的对象）。

    存储位置：这个数据是存储在浏览器进程中的。即使你刷新页面，只要这个历史条目还在，这个 state 就不会丢失。

    位置,状态,类型,行为
    1,http://localhost:3000?tag=m,Document 1,初始加载
    2,http://localhost:3000?tag=m1,Document 1,pushState (无刷新)
    3,http://localhost:3000?tag=m2,Document 1,pushState (无刷新)
    4,http://localhost:3000?tag=d,Document 2,手动输入 (全页面刷新)
    5,http://localhost:3000?tag=d1,Document 2,pushState (无刷新)
    6,http://localhost:3000?tag=d2,Document 2,pushState (无刷新)

    通过 前进，后退 按钮，或者 history.back(), history.forward(), history.go() 方法导航时，会触发 popstate 事件。

    特殊逻辑

    • 浏览器的“无交互记录”跳过机制（User Activation）

      如果一个历史记录是通过 pushState 创建的，但用户在那个状态下没有进行任何实质性的交互（比如点击、滚动、按键），浏览器在点击后退时，可能会认为这些状态是“无意义”的。

      当你手动输入 ?tag=d 后，如果紧接着连续运行了两次 pushState 而没有点击页面任何地方，浏览器在后退时可能会直接把 D1 和 D2 视为 中间过程 直接跳过，一步退回到手动输入的那个 “有来源” 的页面起点。

    • 只有 URL 变化，没有“历史条目”

      在某些特殊的本地测试环境下（比如某些版本的 Live Server 或 Vite HMR 期间），如果你连续快速执行 pushState，而浏览器认为页面内容完全没有变化（DOM 没动），它有时会合并这些连续的 URL 变更。

    • “手动输入”触发了替换（Replace）而不是推送（Push）

      当你从 M2 手动输入 ?tag=d 时，浏览器会认为这是一个全新的导航起点。 如果你在 D 页面加载后，脚本立即执行了 pushState（例如在 onload 或是组件挂载时自动执行），浏览器有时会为了防止死循环，将这种“刚打开就改 URL”的行为处理为 replaceState 效果，导致 D 被 D1 覆盖，D1 被 D2 覆盖。

    • history.replaceState(state, title, url) 修改当前历史记录条目，不会触发 popstate 事件，也不会刷新页面。

    • history.popstate 事件 当活动历史记录条目发生变化时触发（例如用户点击浏览器的后退按钮，或者调用 history.back() 方法）。

简单服务器组件渲染流程

想要使用 RSC 必须要添加 condition 环境变量

在 RSC 架构中，组件被分为两类：

  • 服务端组件 (RSC)：在服务器运行，直接读数据库，禁止使用 useState 或 useEffect。

  • 客户端组件 (CC)：在浏览器运行，可以使用所有 Hook。

在编写服务端组件时，由于 Node.js 环境里依然能引用到完整的 react 包，可能会不小心写下 useState。这时程序不会报错，但会导致逻辑混乱。React 团队通过 exports 条件导出 解决了这个问题： 当 Node.js 开启了 react-server 条件时， import React from ‘react’ 拿到的其实是一个 阉割版的 React，它根本没有 useState 这些导出。一旦你误用，代码在服务器编译阶段就会直接报错，从而保证了 RSC 的纯净性。

创建一个 Server Component

当服务器拦截到客户端页面请求之后, 并不是像 SSR 渲染一样，直接返回渲染后的HTML字符串。而是会通过一个特定的API以流的方式返回给浏览器。

在服务端 (Server Side) 任务是 序列化 (Serialization)。 它将 React 组件树（JSX）转化成一种特殊的、可流式传输的文本格式，最终返回的流的格式如下：

在客户端 (Client Side)，任务是 反序列化与重建 (Reconstruction)。 它通过 createFromFetch 方法接收服务端传来的流，并将其重新“缝合”到浏览器当前的 React 树中。

数据获取

RSC的组件只会在服务端执行，所以它甚至可以直接在组件内部访问数据库，所有的数据获取直接写在组件中，就像是正常的后端代码一样。

它的渲染流程是：

  • root.render 触发，React 进入 Root 组件。

  • use(initialContentPromise) 被调用。此时 fetch 刚刚开始，连第一个 RSC 数据块（Chunk）可能还没解析完。

  • initialContentPromise 处于 Pending 状态。use 钩子会直接“抛出（throw）”这个 Promise。

  • React 捕获到异常，立刻中断 Root 的渲染，转而渲染 loading…

  • 服务器传回了第一批数据（比如 App 的外壳）。

  • createFromFetch 解析了这部分数据，initialContentPromise 的状态被更新。React 被“唤醒”，重新尝试渲染 Root。

  • 这次 use 返回了内容（即包含了两个异步服务端组件占位符的 content）。

    但很快发现：内容里那两个服务端组件因为没用 Suspense 包裹，它们共用了根部的挂起逻辑。如果这两个组件的数据还没到，React 会再次因为它们而挂起,所以继续显示根组件的 loading…,导致 App 外壳必须等到所有子组件加载成功之后才能显示。

所以对于异步组件尽可能的细粒度的控制加载，通过 Suspense 及时渲染已经加载的组件

添加配置文件

在 ZFS 文件系统和快照的机制下，当你“删除”一个文件时，你在文件管理器里确实看不到了，但只要这个文件被任何一个还存活的快照记录了，它所占用的物理磁盘空间就不会被真正释放，直到引用了该文件的最后一个快照被销毁。

但是，这并不意味着所有被删除的文件都会强制保留三年。文件的“物理寿命”取决于它被哪个级别的快照捕捉到了。

我们可以分情况来看：

  1. 昙花一现的文件（寿命极短）
    假设你刚刚新建了一个测试文件，30 分钟后就把它删除了。

这个文件只会被你的 frequently（2 分钟级） 快照捕捉到。

根据你的配置，frequently = 30 意味着高频快照只保留最近 1 小时。

结果： 在你删除该文件 1 小时后，包含了该文件的所有快照都被修剪（Prune）掉了，此时该文件占用的物理空间会真正释放。

  1. 存活了几天或几周的文件
    假设你下载了一部电影，放在那里看了半个月，然后觉得不好看删掉了。

这个文件会被你的 hourly、daily，甚至 weekly 快照捕捉到。

结果： 当它存活在 daily 和 weekly 快照中时，即便你删除了它，它的物理空间也要等到包含它最久远的那个 weekly 快照被删除时（也就是约 4 周后）才会被真正释放。

  1. 被“定格”在年度快照里的文件（寿命最长）
    假设你有一个文档，在你的硬盘里存了很久。Sanoid 的 yearly 快照通常会在每年的 1 月 1 日 00:00 触发。

如果这个文件在某年的 1 月 1 日刚好存在于硬盘中，它就会被写入年度快照。

即使你在 1 月 2 日把这个文件删除了，由于 yearly = 3 的规则，这个 1 月 1 日的快照会被保留整整三年。

结果： 没错，这个文件占用的物理磁盘空间，在未来的三年内绝对不会被释放。

快照被占用

虽然你前端终止了任务，但在底层系统中，这个快照正被某个进程持有了引用计数（Hold），或者底层还有残留的 zfs send/recv 或挂载（Mount/Clone）占用未完全释放。

Replication 底层调用的 zfs send 进程虽然被强行中断，但 Linux/ZFS 内核的管道（Pipe）和套接字缓存（Socket Buffer）往往需要几秒甚至十几秒来彻底关闭网络连接与文件描述符。在这个短暂的释放窗口期内，直接执行普通 zfs destroy 就会报 dataset is busy。

检查是否有快照“持有锁（ZFS Hold）”并释放，Replication 任务在传输时，为了防止快照被其他任务误删，会在快照上打一个叫做 user hold 的标记。任务异常中断时，这个标记可能残留。

如果没有锁，通常是被容器挂载占用、存在未释放的 Clone 克隆卷，或者被 .zfs 隐藏目录缓存占用。请按以下顺序快速定位并强制销毁：

修改 Replication 任务目标端的只读策略，将默认的 REQUIRE 改为 IGNORE（忽略只读检查）或 SET（自动将其强制设为只读）

Replicate Specific Snapshots 不勾选

在生产环境中，本地源端往往为了防误删设置了极高频率的快照（例如 Sanoid 的 frequently 每 2 分钟一次、每小时一次、每天一次，一天能打几百上千个快照）。

不开启此选项：Replication 会把这几百个 2 分钟级的密集快照全部推送到目标端；

开启此选项：你可以指定一个时间窗口粒度（如 Hourly 每小时、Daily 每天、Weekly 每周）。

Only Replicate Snapshots Matching Schedule 不勾选，没有勾选这个选项时的行为（默认）

假设本地用 Sanoid 每 2 分钟打一次快照（frequently），每天产生几百个快照；而 Replication 任务设定为每天凌晨 2 点执行一次：

默认行为：凌晨 2 点任务启动时，系统会把你今天白天产生的几百个 2 分钟级、1 小时级的所有零碎快照，一股脑全量打包发送到目标 NAS。

结果：目标 NAS 会完全镜像你的所有高频快照，导致目标机也存了大量密集快照。

勾选了 Only Replicate Snapshots Matching Schedule 后的行为

过滤行为：Replication 引擎在同步时，会严格比对快照的生成时间点与你 Replication 任务的 Schedule（调度计划）。

结果：如果复制任务设定为“每天凌晨 2 点（Daily）”，那么它只会同步对应在 Daily 时间节点生成的快照；

平时每 2 分钟、每小时产生的零碎快照会被直接过滤掉，不发送到远端。

不要勾选（推荐）：如果你希望目标机是主机的完整镜像，或者希望借助 ZFS 增量传输把过去一整天的历史快照全带过去，保持不勾选。
建议勾选：如果本地打了极其密集的高频快照（如 1 分钟/2 分钟级），但目标 NAS 是异地低速带宽或容量较小，你只想每天/每周同步一个大版本归档快照，则勾选此项。

快照回滚

比“直接回滚”更安全优雅的 2 种找回方式

只找回单个文件：利用隐藏的快照目录（最推荐）

ZFS 在每个数据集的挂载点根目录下都提供了一个隐藏的只读目录：.zfs/snapshot/。

在 SSH 或终端中进入该目录：

你会看到所有历史快照的文件夹，点进对应的快照目录，直接把被误删的文件 cp（复制）回原来的位置即可。

无损恢复：从快照克隆出新数据集,如果你想彻底回到过去的某个完整状态，但又不想破坏之后生成的新快照：

在 TrueNAS Web UI 的快照列表中，找到目标快照，选择 “Clone to new dataset（克隆为新数据集）”。

系统会以零空间占用的方式瞬间生成一个新的独立 Dataset（例如 STORAGE/Document_backup）。

你可以进去核对、提取所需的数据，确认无误后再决定是否替换原数据集。

解析 le\\u0074 x = 5 流程：

  • 实例化 Parser，调用 parse 方法开始解析

  • 初始化 file, grogram 节点

  • 尝试解析 token

    • 跳过空白符，注释等

    • 根据第一个字符判断要如何解析， 比如 l 为一个小写字母， 会被当作 Identifier 解析

    • 尝试读取完成的标识符

      this.state.pos += str <= 0xffff ? 1 : 2; 如果字符 charCode 大于 0xffff 例如 龘, 则向后移动两个字符

      如果匹配到 \, 则判断是否是一个 Unicode 转义序列,后面三位必须是 \\u 开头，如果不是则标记错误

      如果是一个转移字符，尝试读取这个转义字符并返回, 因此第一个 token 会是 let

    • 解析 Program 节点，let 作为 ExpressionStatement 加入 Program 节点，保存在 body 数组中

      继续尝试解析 x = 5 这个表达式作为 AssignmentExpression，x 和 5 作为 Identifier 和 NumericLiteral 加入 AssignmentExpression 分别作为 left 和 right

最终形成的树结构就是 ast.
